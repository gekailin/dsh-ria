# 独立 worker 的可观测性（设计笔记）

日期：2026-11-17
状态：待讨论，不改 DESIGN

## 起因

用户提出：Ria 跟踪独立 worker 后，不是 Ria 派发的任务也许也要了解进度。这样才可能做到帮 worker 提效。

## 问题

- 现在 Ria 只对“自己派发的工单”有账本；独立 worker 由用户直接指挥时，Ria 看不到目标、进度、卡点。
- 看不到过程，就只能等结果；提效建议（补上下文、换工具、拆任务、避免重复失败）无从谈起。
- 但独立 worker 的设定是“独立”：Ria 不能变成第二个指挥者，也不能要求 worker 改配置或强制上报。

## 目标

- 让 Ria 能只读地了解独立 worker 的进度、卡点、产物和上下文。
- 基于观察给出提效建议；建议先给用户，是否转达/执行由用户决定。
- 保持 0 入侵：不注入消息、不改配置、不唤醒 worker、不强制新契约。

## 非目标

- 不接管独立 worker。
- 不直接把独立 worker 改成直管 worker。
- 不默认监视所有会话；需要用户授权/关注。
- 不读与任务无关的隐私内容。

## 可观察面（候选）

- session 状态：running / idle / waiting / error；最后活动时间。
- 消息与工具调用元数据：工具名、耗时、失败次数、文件路径（不一定要读全文）。
- 产物：diff、文件、测试结果、截图。
- 资源：token、时长、重试次数。
- 可选：用户提供的任务目标/验收（否则只能看行为，不能判断“好不好”）。

## 机制候选

1. **只读 observer**：订阅 session 事件，只写 `worker_observation`，不向 worker 注入任何消息。
2. **手动关注**：用户在看板/聊天里说“关注这个 worker”，Ria 才开始观察；默认不主动扫全部会话。
3. **观察记录**：`observed_worker` / `observation`（session_id, task_goal?, status, last_event, signals, artifacts, updated_at），和直管 run record 分开。
4. **提效信号**：长时间无进展、重复失败、上下文缺失、工具误用、可并行/可拆小、适合转直管。
5. **建议出口**：默认只给用户（chat/看板）；用户同意后，Ria 才可以给独立 worker 发普通消息建议。是否允许“直接建议”需要拍板。
6. **任务归属**：Ria 派发的任务有 ticket；非 Ria 派发的任务没有。观察记录可以只有 session 级信息，或由用户补一个 `observed_task` 目标。

## 边界

- 观察 ≠ 指挥：Ria 不直接给独立 worker 下指令。
- 建议 ≠ 修改：Ria 不直接改 worker 的 preset/tools/MCP。
- 用户仍是独立 worker 的指挥者；Ria 的建议经用户转达，或经用户授权后发送。
- 观察数据有范围、保留期、脱敏；用户可随时关闭。

## 开放问题

- 非 Ria 派发的任务，目标/验收从哪里来？用户一句话、worker 自述、还是从 transcript 推断？
- Ria 是否可以主动发现“值得关注”的独立 worker，还是必须用户点名？
- 是否允许 Ria 直接给独立 worker 发建议消息？还是只给用户？
- 观察频率和成本：事件订阅 vs 定期采样；transcript 读多少？
- 独立 worker 是否愿意被观察？要不要在 UI 明示“Ria 正在观察”？
- 观察数据进不进看板？卡片怎么标“观察中”？

## 最小起步

- MVP：用户手动关注一个独立 worker；Ria 只读 session 状态 + 最近消息摘要 + 产物；给用户一条“卡点/建议”。
- 下一步：工具调用元数据、失败模式、跨 worker 对比。
- 再下一步：经用户授权的建议消息；观察记录进看板。

## 和现有设计的关系

- 直管 worker：有 run record，结构化观察。
- 独立 worker：没有契约，只能只读观察；这是治理差异，不是缺陷。
- 看板：增加“观察中”分组/角标；不改变“用户只和 Ria 沟通”。
- Router：非 Ria 任务没有 ticket，Router 不介入；观察由 Ria/observer 负责。若以后要统一，可为 observed task 建轻量记录，但不抢 worker 指挥权。
