# Executor 核心设定

本文定义 `dsh-ria` 中 Executor 的核心模型、通信机制与生命周期约束。所有相关实现须以本文和根目录 [DESIGN.md](../../DESIGN.md) 为准。

## 1. 统一定位

- **统一命名**：项目中所有执行角色统称 `executor`。
- **两类 Executor，一套机制**：
  - **直管 Executor**：Ria 创建并管理的专用会话（常规干活 / 一次性反思复盘），具备 `ria_executor_report` 上报工具；用户在 DSH 界面直连时仅返回固定提示（引导从 Ria 下发任务），不做其他处理。
  - **协管 Executor**：纳入协管的常规会话，**无侵入**（不改会话 preset、prompt、工具集、上下文等，不拦截用户直连消息，但 Ria 须知悉用户直接交代的内容）。
- **除专用上报工具外最大限度统一**：工单流转、路由、注入通道、事件监听与结算、结果落盘与读取、动态打标均复用同一套机制。
- **显式指定约束**：显式指定 Executor 的工单不得静默改派；目标失效时打回用户决策（直管与协管通用）。

## 2. 下行通信

- **工单通道（默认）**：
  - 新任务：Chat 建工单 → Advisor 结合认知记忆生成 WorkOrder → 派发给 Executor（默认附带用户截图等附件）。
  - 追改方向（`steer`）：针对运行中的工单，直接通过 DSH 原生 `steer` 注入给目标 Executor（`rpcId` 使用 `ria_steer_` 前缀），不经 Advisor、不建新工单。
  - **并发与临界隔离（双层串行锁，单向嵌套 `ticketLock → executorLock`）**：
    - `executorLock(executorId)`（主锁）串行保护同一 Executor 的 `dispatch / steer / settle / stop`，`turn/end` 同步入锁；`ticketLock(ticketId)`（辅锁）串行保护 `plan / resume / stop` 的跨异步状态变更。
    - 若 `steer` 拿锁时工单已结案或已切换，直接拒绝并告知 Chat，不向 Executor 发脏消息、不重开旧工单。
    - 若 `steer` 在 `turn/end` 前已写入 DSH inbox 但尚未被当前 turn 消费，`settle` 检测到 `agent.inbox` 中存在 `ria_steer_` 待消费消息时暂缓结算（`steer.settlement.deferred`），等下一轮 `turn/end` 完成后再结案。
    - **迟到 steer 的归属门禁**：工单已结案（done/cancelled/failed）或 Executor 已转跑其它工单时，新的 steer 不入 inbox、不重开旧单、不转交给当前工单；直接丢弃并向 Chat 通知，记录 `steer.dropped_stale`。`agent/pre-step` 同时剥离仍停留在 `ria_steer_` inbox（nextStep/nextTurn）里的过期消息，避免污染下一张工单的上下文。
    - 协管会话在结算临界点遇到用户直连 `steer` 时，绝不拦截且不阻塞原工单结算，新 turn 按无工单协管对话独立处理。
- **直接转发（直转）**：
  - 自然语言单次触发，仅限协管/常规会话（禁止直转给直管 Executor、Sage 等内部角色）。
  - **不建工单、不过 Advisor、Chat 不擅自加工或增删内容**（仅允许修正明显错别字），直接以 DSH 原生 `steer` 方式发送（`rpcId` 使用 `ria_forward_` 前缀）。
- **强制停止**：
  - 支持强制停止，Ria 可按需触发（工单任务走工单停止机制）。
  - 任务被用户手动或异常强制终止后须请示用户，不得擅自重复派发。
- **统一注入通道与来源标识**：
  - 发给 Executor 的所有消息统一走 `kind = user` 注入（直管与协管一致），保持标准 `source: { kind: 'user', rpcId }` 结构。
  - 所有 Ria 注入的 `rpcId` 统一使用 `ria_` 前缀（按用途细分子前缀，如 `ria_steer_`、`ria_forward_`），用以区分 Ria 注入与用户界面直连。

## 3. 事件驱动结算与恢复

- **靠机制不靠看门狗**（定期反思是唯一的看门狗）：靠 DSH 事件与启动检查保证工单有始有终，不新增定时轮询或扫表兜底，也不靠事后去重掩盖重复通知。
- **Report 只记录、不结算**：`ria_executor_report` 仅用于写入结构化进展/结论/阻塞信息，不直接触发工单结算（防止提前/多次调用 `done` 或漏调工具）。
- **统一按生命周期事件结算**：
  - 正常结束以 `turn/end` 为结算时机：已有 report 则采用 report，未调用 report（或协管无 report 工具）则以该 turn 的最终回复兜底。
  - 遇到提问（`ask`）、权限审批、错误中断（含 413 等超长错误）须立即感知并流转/汇报，不得静默卡死。
- **重启恢复**：重启时通过启动检查收尾；`blocked(environment, interrupted)` 的工单自动 `resume` 一次（严格限一次防死循环），Chat 不重复处理。

## 4. 提权审批

- 正常提权走**逐条风险评估**：低风险自动放行，高风险或无法判断上报用户决策，中风险按工单配置决定；`grant` 仅作调试/应急工具。
- 直管与协管的审批与提问事件必须同等监听并及时反馈。

## 5. 上行通知与结果读取

- **通知轻量化**：工单状态通知发给 Chat 时只发状态摘要，不把长正文直接塞入 Chat；发给 Chat 的 Router notice 使用专用 `kind`，Claw 渠道以 `🔔` 前缀区分。
- **分路径读取完整结果**：
  - **有工单任务**（直管/协管统一）：完整结论写入工单，Chat 收到通知后从工单读取，不去翻会话记录。
  - **无工单任务**（如直转）：执行完成后，Chat 读取目标会话对应 turn 的完整回复并回报（不得截断）。

## 6. 元数据、打标与一次性会话

- **直管初始标签非空 & 软亲和路由**：Ria 新建的常规直管 Executor 必须带有非空 `tags`（至少继承触发工单/项目/主题的核心标签），防止产生无标签、后续不再被路由派活的僵尸直管；路由仅做标签软亲和打分，不使用 `requireTagMatch` 硬门槛过滤。
- **动态能力标签（`autotags`）**：直管与协管共用 `autotags`。工单完成后（取消不打标）与跟踪协管会话观察到消息时，**统一走同一套自动打标机制**；按 DSH turn 轮次衰减（阈值约 30 turns），判定时过滤、不删除历史记录。
- **实时状态**：Executor 标题不强缓存、使用时现查；归档状态及时同步并在看板中与活跃 Executor 分离。
- **配置与严格校验**：支持查询可用模型及为会话配置模型、思考强度与权限；工具参数错误或必填缺失必须显式报错。
- **反思 Executor**：每次反思新建独立的一次性反思 Executor，用完即归档。

## 7. 协管与派活开关

- **单一“协管”概念**：`co_manage` 同时覆盖观察（转发回复/提问/审批）与派活。
- **仅用 `allowAutoDispatch` 区分派活范围**：
  - 「协管 / 接管」：`allowAutoDispatch = true`，参与自动路由派单。
  - 「跟踪 / 盯着」：`allowAutoDispatch = false`，仅观察并允许显式指定派单。
  - 显式指定派单或直接转发给未协管的常规会话时，自动纳入协管且默认 `allowAutoDispatch = false`。
- **边界**：
  - 仅监控已协管会话，未协管常规会话事件不得上报通知。
  - 会话归档或删除后，路由必须自动避开，并自动取消协管。
  - 取消协管时保留其历史标签，重新协管后可直接复用。
