# README「经典用法」候选清单

> 用途：给 README 首屏挑示例。每条都是用户对阿汐说的原话，下一行是 README 里的浅色小字解释。
> 统一约束：示例里的 worker 一律用「会话标题」称呼（方案 A），和 DSH 侧边栏看到的文字一致。

## 一、worker 怎么称呼

DSH 里 worker 就是一个有标题的会话（如「Ria开发」「Ria文档治理」「底商3D融入」）。README 的示例要让第一次来的人一眼知道“这是会话，不是同事”。

### 方案 A · 会话标题（推荐）

1. **「阿汐，让『Ria开发』把登录页的验证码换成滑块，今天上线。」**
2. **「阿汐，『底商3D融入』那张新图跑完发我看看。」**

**判断：最容易懂。** 用户在侧边栏看到的就是这行标题，照着念即可，不需要先建立“角色→会话”的映射。

### 方案 B · 角色描述

1. **「阿汐，让前端会话把登录页的验证码换成滑块，今天上线。」**
2. **「阿汐，让底商 3D 会话把那张新图跑完发我看看。」**

**判断：口语最顺，但不够准。** 同一角色有两个会话时，阿汐还得反问“是哪一个”；而且侧边栏里并没有“前端会话”这四个字。

### 方案 C · 短代号 + 注明 worker

1. **「阿汐，让 W1（Ria开发）把登录页的验证码换成滑块，今天上线。」**
2. **「阿汐，让 W2（底商3D融入）把那张新图跑完发我看看。」**

**判断：最不适合 README。** W1/W3 是文档内部编号，用户既看不到也不会说；每次都要先解释编号，反而增加负担。只适合设计稿或测试用例。

**结论：用方案 A。** 标题本身可能带项目名（如「底商3D融入」），但那是用户自己起的名字，比任何抽象角色都好认；下面 12 条也全部按方案 A 写。

## 二、场景候选（12 条）

覆盖：派工、带参考图派活、纠正、配置运维（权限/模型/微信）、验收返工、调研探讨、追问进度、定规则、目标澄清、串行安排。标「主推」的共 7 条。

### 1. 派个明确的活 ｜ 主推

**「阿汐，让『Ria开发』把登录页的验证码换成滑块，今天上线。」**

<sub>她拆好验收条件和步骤，派给这个会话，盯到联调和测试都过，再回来告诉你。</sub>

来源：§4 A 派工（48 条，28.6%）；§5「把 X 改成 Y」「让 XX 做 YY」句式。

### 2. 带参考图派活 ｜ 主推

**「阿汐，这张账单页设计稿发给『Ria开发』，让它照着改，交互别动。」**

<sub>她把图作为附件交给会话，连同“只改视觉、不动交互”的边界一起写进验收。</sub>

来源：§4 H 贴图（32 条，19%）；L6742 的 E2 图 +「用 e2s-1.jpg，重命名并更新文档头图」是同一类“以图代描述”。

### 3. 派错了，先停下 ｜ 主推

**「阿汐，你派错了，先停下——这个活是『底商3D融入』的，不是『无人车底商』。」**

<sub>她先停掉发错的会话，再把任务和上下文转给正确的会话，并告诉你重派结果。</sub>

来源：§4 C 纠正（26 条）；§2 P1-1（T20 L1549「我停掉worker是因为你发错了，不要再发了」）。

### 4. 开权限 ｜ 备选

**「阿汐，给『Ria文档治理』开一下这个仓库的写权限，只开 docs/。」**

<sub>她按最小范围调整权限，改完把生效范围和回滚方式一起告诉你。</sub>

来源：§4 E 配置运维（17 条，10.1%）；旧 README 的临时权限场景。

### 5. 换模型 ｜ 备选

**「阿汐，把『Ria开发』换成 deepseek-v4，再让它接着跑登录页那个活。」**

<sub>她换好模型后把中断的上下文接上，仍按原来的验收标准收尾。</sub>

来源：§4 E 配置运维；现有换模型能力。

### 6. 连接微信 ｜ 备选

**「阿汐，把微信连上，之后任务收尾的消息发到文件传输助手。」**

<sub>她引导你扫码，连好后把收尾汇报同步到微信；连接状态在侧栏「连接」里。</sub>

来源：§4 E 配置运维；T55/T174 的通道反馈；docs/wechat.md。

### 7. 验收返工 ｜ 主推

**「阿汐，搜索结果页的筛选条件没带上，让『Ria开发』返工一版；验收标准是筛选条件必须带上、空结果要有提示。」**

<sub>她把问题写成可验收的标准，退回原会话，改完按同一标准复核。</sub>

来源：§4 D 验收（14 条，8.3%）+ C 纠正（26 条）；§2 P1-2 报障要先要现象。

### 8. 调研探讨 ｜ 主推

**「阿汐，我们聊聊账单页要不要拆成两个 tab，先别动代码。」**

<sub>她先和你把取舍、边界和风险过一遍，等你说“就按这个来”，再落成能派的活。</sub>

来源：§4 F 调研提问（12 条，7.1%）；§5 提问式需求（23 条）。

### 9. 追问进度 ｜ 主推

**「阿汐，『Ria开发』那个登录页的活到哪了？卡住就告诉我卡在哪。」**

<sub>她查一下当前进度，遇到卡点带着原因来问你，而不是等到最后才说“做不完”。</sub>

来源：§4 B 进度追问（10 条，6.0%）；§5「看看/查查」句式。

### 10. 定规则 ｜ 备选

**「阿汐，记一下：以后我说“盯一下『Ria开发』”，就是让你每完成一单都回我一句，不用等我问。」**

<sub>她把这条规则记进长期记忆，之后按这个方式汇报。</sub>

来源：§4 I 规则/记忆（6 条，3.6%）；L7955 的同类原话。

### 11. 目标不清楚，先问一句 ｜ 主推

**「阿汐，让『底商』把新图融入跑一下。」**

<sub>她会先问一句：你说的是会话『底商3D融入』，还是它最近那个“新图融入”的任务？确认后再派。</sub>

来源：§2 P2-5（T10 L796/L907）；§5 实体消歧：先问一句，别先全库检索。

### 12. 串行安排 ｜ 备选

**「阿汐，等支付回调联调完，再让『Ria开发』接后台导出。」**

<sub>她记住先后顺序，前一件没收尾就不催后一件；轮到后者时把上下文一并交过去。</sub>

来源：§5 触发词「先…再」（18 条，11%）；旧 README 的“先做 A 再做 B”。
