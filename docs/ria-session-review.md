## 1. 结论摘要

1. **执行类指令的派工正确率高**：168 条人类消息中 48 条派工类，绝大多数一次到位（建工单→resolve→request→读回执→标 done），返工集中在「目标会话消歧」与「宿主边界操作」两处。
2. **真正的风险不在"做错活"，而在"动宿主"**：手改 session 存储导致会话 corrupt（P0）、两次把 web 杀出 128 s/24 s 空窗（P0）、插件迁移 5 分钟内重启 3 次仍未生效（P1）。
3. **工具语义欠表达制造了 1/3 的无效往返**：目标为空、subagent 不可派、状态机非法迁移、executor 只认 `self`——错误只报"不能"，不报"该怎么写/合法路径是什么"，Ria 只能试。
4. **反馈闭环有漏点**：自己工具崩溃（`ria_status` TypeError）、自己代码写错（run_code 语法错）都不建工单，靠下轮绕过。
5. **文案类交付（口号/图标/hero）缺"一次成型"标准**：口号改 4 轮、"贴近 A3"改 2 轮，都是单点微调而非一次给 5–8 个成型候选。

**意图自动识别评估**

- **规则足够（覆盖约 55%）**：单动词运维指令、`把X改成Y`、`看看X`、`记一下…`、`顺便/另外/插播` 切分、多任务分号切分。实现形态：turn 级分类器（词典 + 正则槽位）+ 切分器 → 每段一个 intent + 实体槽。
- **需检索/语义（约 30%）**：`让XX做YY` 的 XX 消歧（会话标题 vs worker 别名 vs 项目名）、`它/这个/上一条` 回指、"无人机底商 vs 无人车底商"近形词。实现形态：实体解析器查 `ria_status`/`ria_ticket`/会话标题，命中多个时只问一句"是 A 还是 B"。
- **必须语义 + 上下文绑定（约 15%）**：`实现之/可以/上线/保持现状` 这类决策词必须绑定上一轮 assistant 给出的候选集；反馈式微调需抽 direction+target。
- **建议的落地顺序**：先做"单动词指令 + 多任务切分"（低风险、收益立现），再做"实体消歧 + 回指确认"，最后做"决策词绑定"。任何一类在置信度低于阈值时，用一句澄清代替猜测——本次日志里 5 次误派的代价都高于一次澄清。
